A reinstall no longer turns a Mac into a second machine on your board because
its hostname changed, which on macOS it does with the network. The hosted
server caps how many new boards it makes in an hour, not only how many each
address makes, and the web pages say so when they refuse one. Operators get a
runbook that flags, and never deletes, the rows servers before 1.6.2 kept past
its bounds. The Docker image is built with nothing running under emulation, and
CI builds the arm64 image before a release has to. Both phone apps are staged
at 1.6.2 for their stores.

## A reinstall no longer gives a Mac a second machine id

Focus finds the machine a card runs on by an id the listener installer creates
once, at random, in `machine.json`; the board only ever sees a hash of it.
Since 1.4.0 the installer has also kept the hostname it saw, and minted a new
id whenever the next hostname was different, taking that to mean the file had
been copied from another computer. On macOS the hostname does not belong to the
machine: it follows the network (Bonjour, DHCP). The maintainer's Mac wrote
"Mac" on October 5 and read "MacBook-Pro-5.local" on October 19, with its
computer name unchanged, so the 1.6.2 upgrade gave it a second id. The board
showed that Mac twice, and Focus showed it offline on every card that had last
reported under the old id. Any reinstall on another network could have done the
same.

The hardware decides now. The installer reads the Mac's hardware UUID
(`IOPlatformUUID`, from `/usr/sbin/ioreg`) and writes into `machine.json` a
hash of it salted with the machine's own random id, never the UUID itself. On
the next install:

| `machine.json` | What the installer does |
| --- | --- |
| Its hash matches this Mac | Keeps the id. |
| Its hash is another computer's | The file was copied, by a restored backup or a migrated home folder. It warns, naming the hostname the file was last installed as, and gives this Mac an id of its own, as before. |
| It has no hash, as every install before 1.6.3 | Adopts this Mac: writes the hash and keeps the id. |
| The UUID cannot be read | Keeps the id and any hash already there, and warns. |

The hostname is still written, as a hint for people, and nothing compares it.
A damaged hash is read as no hash, so it leads to adoption, never to a second
id. `agstatus listener doctor` reports which of the four it is, instead of
warning that a reinstall would mint a new id: ✔ when the hash matches, ✖ when
it is another computer's (`agstatus listener install` gives this Mac its own
id), a note when no hash is recorded yet, and ⚠ when the UUID cannot be read,
since a copy would then go unnoticed.

**An id that 1.6.2 already replaced stays replaced.** The upgrade adopts the id
the Mac has now, and nothing remembers the one before it. If 1.6.2 gave your
Mac a second id, cards that reported under the old one move to the new one as
their sessions post again, and a session that never posts again leaves the
board when it expires, as any quiet session does.

**What is read, and what is kept.** The UUID is read on your Mac when the
listener is installed or checked, and is not stored. The salted hash stays in
`machine.json`, a local file. Neither is sent anywhere, and the privacy policy,
dated October 21, 2026, now says so.

## New boards are capped server-wide

Every bound 1.6.2 added is per board, and a board costs one request to make.
The only limit on making them was 20 an hour per IP address, and the rate
limiter counts every IPv6 address on its own, so one /64 network is as many
addresses as anyone could want. 500 IPv4 addresses could reach the
10,000-board ceiling within an hour, each board bringing the whole per-board
allowance with it.

`POST /api/workspaces` now also refuses past **200 new boards in any 60
minutes, server-wide**. It is a sliding window rather than a clock hour, which
would let 400 through across the boundary. The refusal is a `503` with a
`Retry-After` giving the seconds until the oldest of those 200 is an hour old,
which is exactly when the next board can be made, and the error reads "too many
workspaces were created on this server in the last hour, try again in 12
minutes". Only boards actually created count, deleted ones included. A refused
request does not, so refusals cannot hold the window shut, and none of them
spends any of the caller's 20. With Postgres the count is read back from the
boards' creation times at startup, because every push to master restarts
agstatus.online and would otherwise hand out a fresh hour. The `MAX_WORKSPACES`
ceiling still answers first, with no `Retry-After`, since nothing says when a
board will be deleted.

It is a `503` and not a `429` because of what the released clients already
say. For a `503` the CLI, the iOS app and the unpublished Android app say the
server is at capacity right now; for a `429` the CLI blames your address and
the phones tell you to wait a moment. The plugin shows the server's own error,
and both installers run the CLI. None of them needed a change, and none retries
on its own.

**What you will not notice.** Making a board is one click, tap or run per
person, and a second machine or phone joins a board by pairing code or URL,
which makes none. 200 an hour is a room of 200 people following a demo at once,
from 200 addresses; behind one venue's NAT the per-address 20 is still the
limit that binds.

**What the web pages say.** The landing page and the web board's welcome
screen said "Could not create a board. Please try again." for any `503`, and
the next click failed the same way. They now say "This server isn't taking new
boards right now. Try again in N minutes.", from `Retry-After`, or "Try again
later." without one. They ship with the server.

**The number is a setting.** Nothing records the hosted board's real busiest
hour, so the 200 is `MAX_NEW_WORKSPACES_PER_HOUR`: a whole number, at least 1,
on multi-tenant servers only, and passed through by `docker-compose.yml`. An
unset or empty value keeps 200 without a warning, so the startup log now prints
the number in force:

```
Limit:     200 new workspaces in any 60 minutes, server-wide (MAX_NEW_WORKSPACES_PER_HOUR)
```

Compose reads `.env` only from the directory it runs in, so the setting goes in
the `.env` beside `docker-compose.yml`. The self-hosting guide's
production-deploy section still described the droplet agstatus.online has left;
it now describes the self-hosted runner that deploys it and names the checkout
whose `.env` that is. The guide also has the query that reads your own
instance's five busiest hours off its boards' creation times
([configuration](https://agstatus.online/docs#self-hosting-configuration)), and
[the API reference](https://agstatus.online/docs#api-limits) lists all three
limits on creation.

## A runbook for rows written before 1.6.2's bounds

1.6.2 bounds what one board's token can make the server keep, and what it loads
at startup, but it changed nothing already on disk. A server that ran an earlier
version can still hold rows written past those bounds: project days dated
`9999-99-99` or outside the 90-day window, project days past 5,000 on a board,
session totals past 550, limit-history series past 48. 1.6.2 never loads them,
so they cost disk rather than memory, and they are still live rows.

[`scripts/flag-flood-rows.sql`](https://github.com/KardanovIR/agstatus/blob/v1.6.3/scripts/flag-flood-rows.sql)
flags them with `UPDATE … SET deleted_at`, the soft delete the server uses
everywhere; there is no `DELETE`, `TRUNCATE` or `DROP` in the file. It touches
only rows that a 1.6.2 restart does not load at that moment and that no later
load can reach, so a restart after it loads what a restart before it would
have. The one exception is a cap that falls inside a tie: Postgres picks which
of the tied rows fill the last places, and that pick can change, never how many
rows load. On a board past 550 session totals that is the usual case, because
every row of one report shares a timestamp.

It is run by hand, in three steps:

- **`mode=diagnose`** only reads: rows per table and per board, the boards over
  each bound, the plan, and how long each board is expected to hold the lock.
- **`mode=dryrun`**, the default, flags each board in its own transaction,
  checks the result, and rolls back.
- **`mode=commit`** does the same and commits each board in turn. A second run
  flags nothing.

While one board's transaction runs, the server's writes to every board wait in
its memory. The wait grows with that board's rows, roughly 12 s per million
live usage rows plus 30 s per million it flags on a 2024 laptop, and floods of
a few thousand rows take well under a second. Do not restart or redeploy the
server during a run, because the waiting writes exist only in its memory. A run
that stops exits with status 3, rolls back the board it was on, and keeps the
boards it already committed. Running again cures a lock timeout; a statement
timeout needs a larger `-v statement_timeout`. Rows that are only past their
retention are reported and left alone unless you add `-v aged=flag`.

Flagged rows stay on disk like every row the server deletes, and the purge in
the self-hosting guide removes them if you want them gone. Its list of tables
now includes `usage_session_totals`, which it had missed, so a purge that
followed the old list left a deleted board's session totals behind. The command
lines, for Compose and for plain `psql`, are in
[the self-hosting guide](https://agstatus.online/docs#self-hosting-flagging-rows-written-before-162s-bounds).

## The Docker image builds without emulation

1.6.2's image was late. Its "Docker image → ghcr" job hung twice the same way:
in the linux/arm64 build stage, `npm ci` under QEMU crashed with an illegal
instruction about 16 s in and then hung until the job's 45-minute timeout,
while amd64 finished in 5 s. The third attempt went through, and the release
was published about an hour and a half after its tag.

The Dockerfile's build stage now runs once, on the builder's own platform
(`FROM --platform=$BUILDPLATFORM`), and each platform's image copies
`node_modules` and `dist` from that one run, so nothing executes for the other
platform. That is sound only while everything the server needs at run time is
plain JavaScript, and it is: express, express-rate-limit, pg and what they pull
in, with no native module among them. A step at the end of the build stage
refuses a native module, so one added later fails the build instead of shipping
the builder's binary to the other platform. The build stage's output was
compared file for file with the old emulated build's, and is identical.

`scripts/check-dockerfile-platforms.sh` refuses any `RUN` in a stage that is
not pinned to the build platform. BuildKit ships its own QEMU and would
otherwise run such a step under emulation, quietly, as 1.6.2's `npm ci` ran.
CI's docker job runs the check and now builds linux/amd64 and linux/arm64,
pushing nothing, so the arm64 image is no longer built for the first time at
the tag. The release workflow runs the check too, since it does not wait for
CI. Its image job times out at 15 minutes instead of 45, and CI's at 15 as
well.

**Building the image yourself needs BuildKit**, the default since Docker Engine
23 and in Compose v2. The legacy builder (`DOCKER_BUILDKIT=0`) stops at its
first step with "failed to parse platform".

## Both phone apps are staged at 1.6.2

1.6.2's pairing fix is app code, so it reaches phones only with new store
builds. Both are prepared and neither is submitted: the iOS project is at 1.6.2
(build 7) and Android at 1.6.2 (versionCode 6). Neither app has changed since
1.6.2, so this release leaves both at that version. With them comes the store
text, and fixes to copy that had stopped being true:

- **The App Store's What's New** covers the pairing check, the card
  separator's contrast fix and the new Source link. If 1.5.0 never left review,
  1.5.0's text goes after it, and that text says Focus is opt-in; the installer
  has set Focus up by default on macOS since 1.4, so the listing gives the
  sentence to paste instead.
- **The App Store description** no longer says blocked cards glow and finished
  ones fade (since 1.5.0 only a stale card dims), or that the app is designed
  for iPhone (it has been universal since 1.2.0).
- **The Play description's privacy paragraph** says what the privacy policy
  says, including what Focus adds to a status post, instead of ending "Nothing
  else." Its What's New is first-release text, since the Android app has never
  been published.
- **The Play checklist** gained the two gates it skipped: the privacy policy
  still says the Android client is not published to any store and has to
  change first, and a new personal developer account needs a closed test with
  12 or more testers for 14 days before it can release to production.
- **`make-upload-keystore.sh`** looked for the Play upload key where it no
  longer is, so it could have minted a second key, and the first upload would
  have registered that one. It now refuses while the key exists in any of the
  folders it knows, old or moved, or the checkout already has
  `keystore.properties`, and `build-play-bundle.sh` no longer suggests making
  a key.

## Upgrading

```bash
curl -fsSL https://agstatus.online/install.sh | sh
```

Same command for a first install and an upgrade, and it keeps the board you
already have. On Windows it is `irm https://agstatus.online/install.ps1 | iex`.
On macOS the upgrade reinstalls the Focus listener, and that reinstall is what
records the hardware hash: an existing machine is adopted and keeps the id it
has now, and `agstatus listener doctor` then says `machine.json` was written on
this machine. With `--no-focus` the installer leaves the listener alone, and
the next `agstatus listener install` adopts the Mac the same way.

The hook is the same code as 1.6.1, and nothing in the plugin but its version
has changed since 1.6.2 — the version moves so the installer, the plugin and
the server image agree — so updating the Claude Code plugin from `/plugin` is
optional.

**Self-hosting.** The cap on new boards is server code. Pull
`ghcr.io/kardanovir/agstatus:1.6.3` (also tagged `1.6` and `latest`) and
restart, or pull the repository and run `docker compose up -d --build`, which
needs BuildKit. A multi-tenant server takes 200 new boards an hour unless you
set `MAX_NEW_WORKSPACES_PER_HOUR` in the `.env` beside `docker-compose.yml`;
the startup log's `Limit:` line shows the number in force. If your server ran a
version before 1.6.2, `scripts/flag-flood-rows.sql` is there when you want it,
and nothing requires it.

iOS and Android do not change in this release. The 1.6.2 builds staged for
the stores reach phones only through store releases, and the Android client is
still not published anywhere.
