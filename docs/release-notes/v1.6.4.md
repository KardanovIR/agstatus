An upgrade now keeps what each machine was set up with. Re-running the install
command used to move a machine on a self-hosted server to a new board on
agstatus.online, sending its sessions there, and to undo `--minimal`, the
webhook secret and a Focus opt-out; it keeps all four now. Codex Desktop's own
short threads, for its suggestions, commit and PR messages and inline edits, no
longer put cards on your board; side conversations and approval requests, which
have a person in them, still do. The Docker Compose stack's network gets a
pinned subnet, so Docker can no longer give it a block that contains the
host's LAN, as it did on the machine that serves agstatus.online. And the
server stops when it is asked to, instead of being killed ten seconds later
with writes still queued. A self-hosted Compose stack takes one `down` before
the `up` this time; the Upgrading section below has the commands.

## An upgrade keeps what the machine was set up with

The install command is also the upgrade, and the installer hands
`agstatus init` only the options given that time. init took everything else
from its defaults, so the documented upgrade undid choices made at install:

- **The server.** Without `--url`, init used agstatus.online and kept a board
  only if it was there. A machine that reported to your own server got a new
  board on agstatus.online instead, its Claude Code and Codex hooks were
  pointed at it, and its sessions went to the hosted service, command text and
  prompts included.
- **`--minimal` and `--secret`.** Both were written only from that run's flags,
  so an upgrade without them removed them, and a machine set up with
  `--minimal` started sending command text, prompts and session titles again.
- **Focus.** The macOS installer set the listener up on every run, after
  `--no-focus` or `agstatus listener uninstall` too.

The notes of 1.5.2 and 1.6.1 to 1.6.3 said the command keeps the board you
already have, which held only on agstatus.online.

init now reads the machine's setup before it decides anything, from the files
its hooks are configured with:

- It connects to the server that Claude Code's settings, or else the Codex
  hook, already post to, unless `--url` or `AGSTATUS_URL` names another, and
  says so on its first line. Neither the shell's environment nor
  `~/.agstatus.json` chooses it.
- `--minimal` stays until `--no-minimal`.
- A webhook secret stays until `--no-secret`, and only for the single-tenant
  server it was set up for: a move to another server leaves it behind.
- Each option it keeps is named in its output.
- If `~/.claude/settings.json` or `~/.agstatus.json` exists but cannot be
  read, init stops before it reaches any server and says which file to fix.
  It used to carry on and make a new board.

The Focus listener and `agstatus focus` follow the same rule: they send a
webhook secret only to the server it was set up for. Before, a secret
configured for Codex on one single-tenant server could go out with every
request to Claude Code's board on another.

A pairing code given without `--url` is claimed on agstatus.online, wherever
the machine reports now, which is what the apps' "Pair your computer" command
assumes. On Windows the new switches are `-NoMinimal` and `-NoSecret`.

On macOS, `"focus": false` in `~/.agstatus.json` now means Focus was turned
off on this Mac, and the installer leaves it off until `--focus` or
`agstatus listener install`. `agstatus listener uninstall` writes it, and so
does `--no-focus`, which now turns Focus off through that command, even when
init fails. An upgrade over an install where Focus was not on keeps it off as
well, because `--no-focus` used to leave no record; a Mac whose last
`listener install` failed stays off too, until `--focus`. `agstatus uninstall`
writes `"focus": false` as well, so a reinstall after one starts with Focus off
and says how to turn it on.

`--no-codex` is still not kept: on a machine with `~/.codex`, give it again or
the upgrade sets Codex up. The privacy policy said that re-running the
installer without `--minimal` removes it. It now says the switch stays until
`--no-minimal`, and that Focus stays off once turned off.

## Codex Desktop's helper runs stay off the board

Codex Desktop starts threads for itself. Each suggestion it prepares for a
project is a run in the project folder and then a check in `/`, and it writes
commit and PR messages and inline edits the same way. Those threads ran the
hook like any session, so each one became a Codex card, named after the project
(or "Codex", for the check in `/`) and left at done, beside the session you
were actually in. On the maintainer's Mac, 85 of the 96 Codex sessions the hook
had recorded were suggestion runs, and two cards with one project's name read
as a session and its sub-agent.

Codex keeps a rollout, its saved transcript, for every thread you can come back
to, and every hook event names it in `transcript_path`. These threads keep
none, and say so with `transcript_path: null`. The hook now drops such a
thread's events before it sends or stores anything.

Two things keep a thread with no rollout on the board, because a person is in
it:

- **It is a side conversation**: Desktop's side chats, `/side` in the TUI and
  `codex exec fork --ephemeral`. They fork a session, which their
  `SessionStart` says with `source: "fork"` from Codex 0.155, and the hook
  keeps the thread from then on.
- **It asks for approval.** An approval request always posts, from whichever
  thread, and keeps that thread on the board afterwards. A side conversation
  the hook never saw start, on a Codex before 0.155, therefore appears at its
  first approval request, and one already running when you upgrade keeps the
  card it had, which stops updating until then.

Sub-agents go with their thread: a saved session's sub-agents name their own
rollouts and keep posting, and a helper run's sub-agents are dropped with it. A
fresh `codex exec --ephemeral` run is ignored along with the helpers, and Claude
Code's events are never filtered.

On agstatus.online, helper cards already on your board leave 24 hours after
their last update, as any quiet session does. A self-hosted board in
single-tenant mode, the default, expires no session unless `SESSION_TTL_MS` is
set, so dismiss those cards yourself: × on the web board, swipe on a phone.

## The Compose network can no longer swallow your LAN

Docker gives each new network a subnet from its pools: 172.17 to 172.31 first,
then blocks of 192.168.x.0/20. On the machine that serves agstatus.online the
first pools were used up, and the stack's network was given 192.168.0.0/20,
which contains the host's LAN. The route for that block pointed into the
network, so every container on the host sent its LAN traffic there instead of
out to the LAN: other services on the machine could reach no LAN device, and a
reverse proxy there answered 504.

`docker-compose.yml` now pins the subnet to `172.16.80.0/24`: private, outside
both of Docker's default pools, and outside the 10.0.0.0/8 that VPNs and
offices favour. Set `AGSTATUS_SUBNET` in the `.env` beside `docker-compose.yml`
if that clashes with something on your LAN or VPN, or with another stack on the
host.

A network keeps the subnet it was created with, so an existing install moves
onto the pin only when its network is made again, by a `down` and then an `up`.
Don't skip the `down`. Given a plain `up -d`, Compose 2.31 and later rebuilds
the network in place and reattaches the old containers without their service
names, so the server can no longer reach `postgres`. The commands, and the
repair if that has already happened, are under Upgrading.

agstatus.online now deploys with
[`scripts/deploy-compose-up.sh`](https://github.com/KardanovIR/agstatus/blob/v1.6.4/scripts/deploy-compose-up.sh).
When the network is not on the configured subnet, the script first checks that
nothing outside the stack is attached to it and that Docker accepts the subnet.
Then it builds the image, takes the stack down (never with `-v`), brings it up,
and logs the database's row counts from before and after. After every `up` it
also checks that each container answers to its service name, and recreates the
containers if one doesn't. The swap took agstatus.online down for about 40
seconds on November 3, every board and session came through it, and the deploys
since have left the network alone.

## The server stops when asked

The server ran as its container's PID 1 with no handler for SIGTERM, and PID 1
ignores a signal it has no handler for. Every `docker stop` waited out Docker's
10 s timeout and then killed the server with SIGKILL, along with any writes
still queued for Postgres, and every deploy that replaced it waited the same
10 s.

On SIGTERM or SIGINT the server now stops taking connections, ends every event
stream, lets the requests already running finish, writes what is still queued
to Postgres and exits, normally in a fraction of a second. Connections still
open after 2 s are cut, and if it is not done 4 s after the signal it logs so
and exits anyway, well inside Docker's 10 s. A stream ends with no final event,
because the board is still there, and one asked for during shutdown gets `503`.
The web board, both phone apps and the CLI's listener reconnect by themselves.
`docker-compose.yml` also runs the server under Docker's init (`init: true`),
so it is no longer PID 1. On agstatus.online, replacing the server took 1.4 s
on the next deploy, where it had taken 10 to 12 s.

The Cloudflare Tunnel connector in `docker-compose.yml` now gives requests in
flight 2 s when it stops (`--grace-period 2s`), not its default 30 s. While the
server is up, an open event stream is always in flight, so stopping the
connector with the server still running, as every `down` does, ran into
Docker's 10 s timeout too.

## Upgrading

```bash
curl -fsSL https://agstatus.online/install.sh | sh
```

Same command for a first install and an upgrade; on Windows it is
`irm https://agstatus.online/install.ps1 | iex`. This upgrade already runs the
new `agstatus init`, so it needs none of the options a machine was installed
with: a machine on your own server stays there, and `--minimal`, the secret
and a Focus opt-out stay as they are. Only `--no-codex` has to be given again.
The Focus part lives in the install script itself, so a machine that fetches
the script from a self-hosted server gets it once that server runs 1.6.4.

When it finds Codex, the upgrade copies the new hook into Codex's hooks folder
(`$CODEX_HOME/hooks`, by default `~/.codex/hooks`) and registers the same
command every release since 1.4.0 has. Codex trusts a hook by a hash of its
command, so it keeps running this one, and you are not asked to trust it again.
A Codex hook installed by 1.3 or earlier carried its settings in its command,
so that command changes once, and the installer tells you to trust it again:
`/hooks` in the Codex CLI, Settings → Hooks in Codex Desktop.

The hook in the Claude Code plugin is the same file, but its change concerns
only Codex, and the plugin has no `init` to change, so updating the plugin from
`/plugin` is optional; the version moves so the installer, the plugin and the
server image agree.

**Self-hosting with the image.** The shutdown handling is server code. Pull
`ghcr.io/kardanovir/agstatus:1.6.4` (also tagged `1.6` and `latest`) and
restart. The server handles SIGTERM itself, so an init process (`init: true`,
`docker run --init`) is optional.

**Self-hosting with the repository's `docker-compose.yml`.** Pull, build, and
take the stack down once before bringing it up, with the `--profile` flags you
always use (`tunnel` for the Cloudflare connector, `tls` for Caddy, none for
neither):

```bash
git pull
docker compose --profile tunnel build
docker compose --profile tunnel down
docker compose --profile tunnel up -d
```

Never add `-v` to `down`: the `pg_data` volume is the database. Building first
keeps the stack down only for the restart. If `172.16.80.0/24` is already used
on your LAN or VPN, or by another Docker network on the host, set
`AGSTATUS_SUBNET` in `.env` before the `up`. If you ran a plain `up -d` first,
the containers came back unable to find each other by name, and
`docker compose --profile tunnel up -d --force-recreate` puts it right. A
droplet set up with `deploy/bootstrap-droplet.sh` needs
`docker compose --profile tls down` in `/opt/agstatus` before the script is run
again.

If your stack's network was on a 192.168.x.0/20 block, Docker can give that
block to the next network it creates for anything else. The Docker daemon's
`default-address-pools` setting is how to keep new networks off your LAN;
leave the stack's own subnet out of the pools you give it.

Neither phone app changes in this release.
