The repository was renamed from `claude-status-dashboard` to `agstatus`, and
from that moment every install and every upgrade stopped before it downloaded
anything. Both installers work again, and the next rename will not break them.
The server now puts a ceiling on what one board can make it keep, on disk as
well as in memory. And the pair command the phone apps put on your screen no
longer takes the board's word for what goes into it.

## The installers work again after the repo rename

Both installers ask GitHub for `/releases/latest` and read the one redirect it
answers with, which names the newest tag: `/releases/tag/vX.Y.Z`. After the
rename, the old name's `/releases/latest` answered with a different redirect
first — to the new name's `/releases/latest` — and only that one names the
tag. `install.sh` took the whole URL for the version and stopped with "The
latest release does not look like a version we can install"; `install.ps1`
stopped with "could not read a version tag out of the redirect target".
Neither had installed or changed anything by then. Only `install.sh` on a
machine with wget and no curl kept working, because wget follows redirects.

Both installers name the new repository now, and they survive the next rename
without waiting for that edit: a redirect to another repository's
`/releases/latest` on github.com, over https, is asked again, up to three
times. Anything else is still read as the answer and still has to name a
release tag. The curl and PowerShell lookups follow no other redirect (wget,
as before, follows them all), and no lookup calls GitHub's API. The downloads
needed no change: GitHub redirects a renamed repository's release files too,
and both installers already followed that.

When the lookup failed, `install.sh` suggested pinning
`AGSTATUS_VERSION=1.3.0`. 1.3.0 and every release before it shipped through
npm and Homebrew and have nothing for the installer to download, so following
the hint always ended in a 404 — and it was printed exactly when the rename
broke the lookup. The hints say `X.Y.Z` now and point at the releases page;
1.4.0 is the oldest release the installer can install.

**The fix is in the installers, and agstatus.online serves them**, so the
one-liner works again without upgrading anything first. A copy of `install.sh`
saved to disk before now still names the old repository and still fails the
lookup. Fetch it again, or pin a version, which skips the lookup — the
download itself follows the redirect:

```bash
AGSTATUS_VERSION=1.6.2 sh install.sh
```

`install.ps1` has no pin, so a saved copy of it has to be fetched again.

## The server bounds what one board can make it keep

A board's token was enough to make the server store an unbounded amount.
`/usage/projects` capped a report at 200 rows and nothing else, so one token
could add tens of thousands of permanent rows a minute — and a day only had to
look like `dddd-dd-dd`, so `9999-99-99` outlived every restart and was loaded
back whole. Session totals, push devices and limit history did have caps, but
each made room by dropping or flagging an old entry, which bounds memory and
still lets the table grow.

Every cap now **refuses the new thing and keeps updating what it already
holds**, because that is the only kind of bound that holds on disk too.
Nothing is deleted; rows that age out are flagged, as before. The caps are per
board, on agstatus.online and on a self-hosted server alike:

| What | Cap |
| --- | --- |
| Usage sources | 8, across `/usage`, `/usage/projects` and `/usage/sessions` |
| Project days | real dates from 90 days ago through tomorrow (UTC), and 5,000 (source, project, day) keys |
| Limit history | 48 (source, window) series, at most one point per series a minute |
| Per-session totals | 500, or 550 for sessions that have a card on the board |
| Push device tokens | 100, counting the ones unregistered in the last 90 days, and 10 registrations a minute |
| Usage-history reads | 30 a minute |

**What you will not notice.** The bundled hooks report two sources, `claude`
and `codex`. The maintainer's own board — every agent workflow in its own
worktree folder — held 278 project-day rows over 90 days, and at its busiest
day's folder count a full 90 days would be about 2,950. The charts sample
limit history once a day and the hooks report at most every five minutes, so
a point a minute costs no chart anything. `--backfill` still sends everything
your logs hold; days older than 90 are skipped rather than stored, and nothing
ever showed them, because history reads stop at 90 days. Session-history `seq`
values are now numbered per board rather than per session, so they have gaps;
the clients need them only to be unique and increasing, which they still are.

**What you might:**

- A board that reports token totals for more than 500 sessions inside a week
  stops admitting new ones, except for sessions with a card on the board, up
  to 550. A session refused there shows no token number on its card until
  older totals pass their 7-day retention and give their slots back. Before,
  the oldest total was dropped to make room.
- A board that holds 100 push tokens — the live ones plus the ones
  unregistered in the last 90 days — refuses a new one until 90 days after one
  of them was unregistered. Reinstalls, restores, new phones, simulators and
  switches between sandbox and production builds each get a new token. The iOS app shows the refusal as the
  notifications switch turning itself off; showing the server's reason is a
  client change, and is not in this release.
- Registering a phone for notifications more than ten times in a minute is
  refused too, until the minute is up. The count is per board: switching
  notifications on, changing the "Each time an agent finishes a turn" switch,
  and every phone's re-registration when the app starts all count toward it.
  The iOS app shows a refused switch-on as the switch turning itself off. A
  refused change to the finished-turn switch shows nothing: the switch moves,
  but the board keeps the old setting until the app is next started from
  scratch. Switching notifications off and disconnecting from a board are
  never refused.

**Two responses gained fields**, and neither lost one. `POST /usage/projects`
answers `{"ok": true, "days": N, "dropped": D, "refused": R}`: `days` counts
the rows stored, `dropped` the rows whose day does not exist or lies outside
the window, and `refused` the new keys the board had no room for. `POST
/usage/sessions` answers `{"ok": true, "sessions": N, "refused": R}`. A
project-day token count above `Number.MAX_SAFE_INTEGER` is a `400` now, as it
already was for session totals. Every limit is listed in
[the API reference](https://agstatus.online/docs#api-limits).

## The pair command no longer trusts the board, on both phones

The Pair sheet builds the one line it tells you to paste into a terminal:

```bash
curl -fsSL https://agstatus.online/install.sh | sh -s -- --code 'ABCD-EFGH'
```

Both apps put two values from the board into that line unquoted: the pairing
code and, for a self-hosted board, the board's address after `--url`. A board
that answered with a "code" such as `ABCD-EFGH; <any command> #` had that
command run by whoever pasted the line. agstatus.online gains nothing from
that, since it already serves the installer the line pipes into `sh`. Any
other board gains exactly what the installer's pinned download and checksum
otherwise deny it.

Both apps now accept only a code the server could have generated — eight
characters from its alphabet, shown as `XXXX-XXXX` — and show anything else as
an unexpected server response, never as a command. A board's address is held
to the characters a host name can contain, and both values are single-quoted
as well, as a backstop. On Android the address is also rebuilt from its
parsed scheme, host and port instead of being kept as typed or scanned, and a
saved board is repaired the same way when the app loads it; one that cannot be
repaired is forgotten on that device only, as "Disconnect this device" would.
The iPhone app does not re-check a saved board, but quotes its address in the
line all the same. Boards with non-ASCII names, like `https://bücher.example`,
and hosts with an underscore, like `https://my_host.example`, work on both.
Plain HTTP on a local network, like `http://dev_pc.local:3000`, works on the
iPhone only: Android allows plain HTTP only to localhost and to the emulator's
10.0.2.2.

This reaches you with the next iOS build. The Android client is still not
published anywhere.

## Links name the renamed repository

GitHub redirects the old name for now, but only until another repository takes
it, and that redirect is what broke the installers. So every link and manifest
names `KardanovIR/agstatus` directly: the README, `SECURITY.md`, the docs, the
landing page, the privacy policy's contact link, both `package.json` files, the
plugin manifest, and the Source links in both apps, which reach you with their
next builds. The Docker Compose file still tags its local build
`claude-status-dashboard`, on purpose: renaming it would orphan the images
self-hosters have already built.

## Upgrading

```bash
curl -fsSL https://agstatus.online/install.sh | sh
```

Same command for a first install and an upgrade, and it keeps the board you
already have. On Windows it is `irm https://agstatus.online/install.ps1 | iex`.
The CLI and the hook are the same code as 1.6.1 — the version moves so the
installer, the plugin and the server image agree — so an upgrade brings a
machine nothing new but the version number, and updating the Claude Code
plugin from `/plugin` is optional.

**Self-hosting.** The new limits are server code. Pull
`ghcr.io/kardanovir/agstatus:1.6.2` (also tagged `1.6` and `latest`) and
restart, or pull the repository and run `docker compose up -d --build`. Rows a
board wrote before this release stay on disk as they are; the server loads only
what the new caps allow.

iOS stays at 1.5.0 and Android at 1.6.0, still unpublished; the pairing fix and
the new Source links reach them with their next builds.
